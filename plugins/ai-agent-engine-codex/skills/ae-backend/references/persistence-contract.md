# Persistence Contract

Apply this reference only when work creates or materially changes durable application data. The target repository remains authoritative for ORM, schema names, ID types, audit conventions, error envelopes, and migration tooling.

## Required Decisions

1. Classify the durable structure: mutable business aggregate, association table, append-only audit/event/outbox table, or reference/dictionary table.
2. For a new durable table, confirm the primary-key strategy before implementation. If repository/user evidence does not decide it, ask exactly: `本次新增持久化表的主键策略选择自增 BIGINT，还是 UUID？是否需要对外暴露该 ID？` Do not default to either option.
3. Record whether the identifier is externally exposed, sortable, generated by the database/application, and subject to enumeration or JavaScript-integer compatibility concerns.
4. Decide audit ownership, deletion/retention and restore semantics, concurrency policy, persisted enum representation, constraints/indexes, migration ordering, rollback, and error translation.

## Conditional Table Governance

- Mutable aggregates may need optimistic locking, audit fields, and logical deletion when the repository and lifecycle justify them.
- Association tables often need only keys, audit fields, and unique constraints; do not add a version or logical deletion marker by habit.
- Append-only audit/event/outbox tables usually favor immutable inserts and explicit retention over logical deletion or optimistic locking.
- Reference/dictionary tables need a stable business code, enable/disable lifecycle, and consumer compatibility; apply audit/deletion/version fields only when local convention requires them.

## MyBatis-Plus (Conditional)

Only a repository that already uses MyBatis-Plus may adopt `@Version`, `@TableLogic`, and `FieldFill` fields. For an applicable mutable aggregate, the usual local pattern can include `version`, `deleted`, `create_by`, `create_time`, `update_by`, and `update_time`; confirm the exact types, meta-object fill handler, and database defaults from repository evidence. Do not add these annotations to other frameworks or non-applicable table types.

## Integrity And API Rules

- Server code owns audit actors and timestamps; clients do not supply authoritative audit values.
- Logical deletion requires query filtering, unique-index behavior, restore policy, related-record handling, and retention to be explicit.
- Optimistic locking requires a defined conflict response and client retry/refresh behavior when a client observes the version.
- Persist enums as stable explicit codes, not language ordinal positions. State unknown and retired-code behavior before consumers or migrations depend on them.
- Translate validation, not-found, state/optimistic conflict, authorization, and infrastructure failures through the repository's established exception handler and response envelope. Do not leak SQL, ORM exceptions, stack traces, or entity internals.

## Verification

For any schema change, verify entity-to-DDL alignment, migration ordering, indexes/constraints, rollback or irreversible-acceptance rationale, and focused behavior tests. Use `ae-sql` for SQL/migration review and `ae-review` with the data-migrations lens before delivery.
