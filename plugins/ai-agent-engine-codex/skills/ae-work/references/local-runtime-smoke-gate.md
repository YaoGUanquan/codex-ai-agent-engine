# Local Runtime Smoke Gate

Use this gate only when the user explicitly asks to start, execute, automatically run, smoke test, bubble test, or locally integrate a changed local API or UI surface. It does not make a live request mandatory for documentation-only work, isolated unit-test work, or a target that has no runnable local surface.

## Preconditions

1. Confirm that the running target can contain the change. Follow a target project's restart or hot-reload rule; do not infer this from a completed build or passing unit tests.
2. Identify the target route or page, expected signal, request fixture, operation graph, and whether the operation is read-only or state-changing. A POST is not automatically safe; use only a preview or query path whose contract proves it does not write state.
3. Build a source-backed request-context manifest before selecting a client. Resolve required headers, cookies, path/query parameters, body fields, and conditional values from complete OpenAPI/Swagger, otherwise controller/DTO plus auth, gateway, filter, or interceptor configuration. Captured requests and user recollection are supporting evidence only.
4. For each request input, record only sanitized metadata: location, requiredness/condition, authoritative source, classification, provider, validation, lifetime, and redaction rule. Classify inputs as static non-secret fixture, user-controlled opaque secret, environment-specific non-secret context, runtime-derived, or prior-response-derived. Include applicable scope, media-type, locale, version/concurrency, idempotency, signature/timestamp/nonce, CSRF/session, and gateway headers; explicitly justify inapplicable categories.
5. Resolve the execution carrier before asking for credentials or a restart: `project runner -> single-request curl fallback -> blocked`. A project runner is mandatory for state-changing, multi-step, read-back, restoration, dynamic-value, signature/nonce, or cross-field validation workflows. Non-GET methods require a project runner unless the contract proves they are read-only. Validate the runner or fallback token-free. Import `plugins/ai-agent-engine-codex/scripts/request-context-contract.mjs` for deterministic eligibility, same-process credential readiness, and outcome classification; it does not send requests or read secrets. A discovered runner that lacks method, path-template, and assertion coverage evidence cannot fall through to curl.
6. For an authenticated request, require a user-controlled local secret reference, such as an ignored curl config file or an environment variable already visible to the executing process. If one is missing, proactively create a token-free request template at a verified ignored project path or in the operating system temporary directory. Follow [the request config template](request-config-template.md): write UTF-8 without BOM through a UTF-8-safe writer, never create an empty or comments-only file, include the bounded route, method, non-secret fixture settings, numbered fill steps, and exactly one `REPLACE_WITH_LOCAL_TOKEN` credential placeholder. Report its absolute path and wait for the user to populate it locally and confirm readiness. A raw credential supplied in chat must not be copied into command text, patches, logs, agent-written files, or tool stdin. After handoff, the agent must not open, read, write, print, or validate the populated reference; it may only pass its absolute path to a client option that consumes the reference without echoing its contents.
7. For a state-changing request, obtain explicit authorization for the exact target and state effect. Prefer a read-only representative request when it proves the requested behavior.

If a precondition or request-context input is missing, contradictory, stale, or has no provider, report the exact sanitized category once and leave runtime validation blocked. Do not repeatedly ask for a prerequisite that the user already confirmed.

## Execute And Record

When the preconditions for a smoke are met, run the bounded request once by referencing the populated secret path or environment variable. An environment variable is valid only as a same-process environment input visible to the executor. The runner must acquire or generate revisions, ETags, timestamps, nonces, signatures, CSRF values, and response-derived identifiers at point of use; never paste them into a reusable template. Do not inspect the reference before or after the request. Record only the route template, carrier class, request-context categories, operation classification, expected signal, actual signal, response status, failure category, and unverified scope. Never echo credentials, concrete header values, cookies, request configuration contents, dynamic values, or private response data. Archive only this sanitized execution evidence; never archive, commit, relocate, or expose a secret reference, and do not delete a user-populated reference without explicit authorization.

Classify the first failure as `request-context`, `client-config`, `transport`, `auth`, or `business` before retry. Map 2xx to `passed`, 5xx to `transport`, 401/403 to `auth`, and other 4xx to `business`. A request-context failure is fixed by resolving the missing or contradictory input; a client-config failure is reproduced token-free before changing the carrier; transport retains the carrier while target health is checked; auth renews the same credential reference; business routes to contract debugging. Treat a 4xx, 5xx, transport failure, or business error as blocked. Do not switch carriers without disconfirming evidence and do not claim a pass until the intended behavior and expected signal are observed.

## Capability Boundary

This gate is a process contract, not a secret manager, server-lifecycle controller, browser registration mechanism, production-access grant, or unattended test runner. Use only tools and local access already available in the current Codex session.
