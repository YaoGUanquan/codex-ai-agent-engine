# 学生管理与班级管理方案补充 PRD

## Background

本 PRD 用于补齐 `20260609 学生管理与班级管理需求文档.docx` 与现有班级管理扩展计划之间的差距。现有计划已经覆盖班主任独立建模、动态当前年级、班级变更日志和关系有效期，但还缺少班级状态闭环、学生管理列表/详情/历史、学生批量导入解析与异常处理。

## Goals

- 班级管理支持状态筛选、状态流转、毕业/停用/归档后不可作为新业务可选班级。
- 当前年级由系统计算，不允许管理员直接修改；最高年级进入下一学年后进入已毕业状态。
- 学生管理支持按入学年份、动态年级、班级、状态筛选，并支持姓名、系统账号、手机号搜索。
- 学生详情展示基础信息、账号绑定状态、学生状态和修改历史。
- 学生新建、修改、状态变更、班级变动和批量导入入库均记录可展示的操作历史。
- 学生批量导入使用新的学生导入接口族，不修改旧的批量导入用户接口。
- 学生批量导入成功后必须同步创建学生 `users` 账号、`user_profile` 学生档案，并与 `student` 学生实体建立绑定。
- 学生导入支持 0 到多个家长手机号；提供手机号时创建或复用家长账号、赋予“学生家长”角色，并建立家长与学生账号关系。
- 家长手机号缺失不阻断学生导入；系统提供后续补录和绑定家长信息的接口。

## Non-Goals

- 不修改 `/api/v1/excel/import/school-user` 等旧批量导入用户接口。
- 不要求复用旧的一步式 `/api/v1/excel/import/student-entity` 作为新学生管理导入页面接口；它可以保留为兼容入口。
- 不在本方案中改造所有作业链路以完整支持学生实体。
- 不在本方案中实现跨学段自动建班、拆班、合班。
- 不在本方案中解决家长手机号是否允许多个学生共用的最终产品规则；该问题保持开放，但接口必须能返回明确校验结果。
- 不修改旧的批量导入用户接口来承载新学生导入；新导入不得复用 `/api/v1/excel/import/school-user` 的入库流程。
- 不在本期实现学生默认密码登录时的家长手机号验证和强制改密拦截；该规则作为后续登录改造需求记录到 AI 记忆库。

## Functional Requirements

### Class Status and Promotion

- 班级状态至少包含：有效、停用、已毕业、归档。
- 班级列表支持按状态筛选，列表字段返回状态。
- 班级创建后默认为有效；修改班级时可变更状态，但当前年级不可直接修改。
- 已毕业、停用、归档班级不能作为新建学生、批量导入、AI 批改任务的新可选班级。
- 年级自动升级按学校学年日历执行。本期产品默认新学年触发日为 8 月 15 日；若项目已有 9 月 1 日规则，需抽成可配置日历服务，避免在多个服务中硬编码不同日期。
- 最高年级进入下一学年时，班级状态变更为已毕业，并记录升级/毕业结果。
- 入学年份、学段、学制规则缺失时，不参与正常升级，并生成异常记录。

### Student Management

- 学生列表支持筛选：入学年份、动态当前年级、班级、学生状态。
- 学生列表支持搜索：姓名、系统账号、手机号。
- 年级和班级筛选联动，选择动态当前年级后，班级下拉仅展示该年级下有效班级。
- 学生详情展示姓名、学号、手机号、性别、动态当前年级、班级、学生状态、系统账号、账号绑定状态、修改历史。
- 新建学生时必须选择或继承有效班级；已毕业、停用、归档班级不可选。
- 修改学生姓名、性别、手机号、状态等关键字段时，写入学生操作历史。
- 学生状态为禁用时，列表保留可见，但不进入新的 AI 批改、任务分配等业务范围。

### New Student Import Workflow

- 新增学生导入接口族，建议挂在 `/api/v1/student/imports` 或 `/api/v1/student/entity/imports`。
- 上传接口只创建导入任务并解析文件，不直接最终入库所有数据。
- 解析任务返回文件名、解析状态、进度、识别学生数、可导入数、需处理数和异常分类。
- 确认导入接口只导入校验通过的数据；异常数据保留为待处理行。
- 异常行支持查询、单条修正、重新校验、忽略、标记待处理。
- 班级不存在时，修正抽屉只允许选择已存在且有效的班级，不在本期快速新建班级。
- 手机号异常必须返回字段级错误原因。
- 重复学生必须返回可处理状态，至少支持合并、忽略此条、标记待处理；具体合并规则可先由后端返回候选与风险提示。
- 导入成功的学生写入学生操作历史，并保留导入任务与行明细用于追踪。

### Student Account Provisioning

- 确认导入成功的每个学生都必须创建或绑定一个学生账号，至少写入：
  - `users`: `username/password_hash/nick_name/user_phone/first_login/school_id/school_name` 等账号基础字段。
  - `user_profile`: `user_id/user_type=2/real_name/phone/gender/student_id/enrollment_date/class_id/class_name/grade_level/student_status` 等学生档案字段。
  - `student`: 记录学生实体与 `users.id` 的绑定字段；若当前实体表已有 `user_id` 字段则复用，若缺失则在实施计划中补齐。
  - `sys_user_role`: 为学生账号分配 `STUDENT` 角色。
- 学生账号名采用“学校编码 + 班级编码 + 学生序号”的确定性规则，目标格式示例为 `520000120260101`。
  - 学校编码建议使用“省份编码 + 学校开通序号”，如 `5200001`。
  - 班级编码建议使用“入学年份 + 班级序号”，如 `202601`。
  - 学生序号默认两位，不足补零。
  - 最终账号必须全局唯一且长度不超过 18 位；发生冲突时通过递增学生序号或短后缀重试，不允许生成超过 18 位的账号。
- 导入学生密码允许使用配置化统一默认密码；入库时按项目现有密码加密工具写入 `password_hash`。
- 系统需要记录学生账号仍处于默认密码状态，便于后续登录改造识别并触发“验证家长手机号 + 强制修改密码”流程。
- 当前代码中学生角色登录仍被拦截；本期创建学生账号用于身份绑定、后续登录能力和家长关系，不代表立即开放学生登录。

### Parent Binding

- 导入模板支持一个或多个家长手机号，建议同时支持关系、是否主监护人等可选信息；多个家长使用结构化列或可解析分隔格式，最终在行明细中保留 JSON 快照。
- 家长手机号可以为空。为空时学生行仍可导入成功，并标记家长绑定状态为 `PARENT_MISSING` 或等价状态，供后续补录。
- 提供学生家长补录接口，用于给已导入学生新增、更新或解绑家长信息。
- 提供家长手机号时：
  - 按学校与手机号查找可复用的家长账号；没有则创建新的 `users` 账号。
  - 写入或补齐 `user_profile` 家长档案，`user_type=3`。
  - 新增角色代码 `STUDENT_PARENT`，显示名“学生家长”，并为家长账号写入 `sys_user_role`。
  - 通过现有 `parent_student` 表建立 `parent_id=家长 users.id` 与 `student_id=学生 users.id` 的关系，支持多个家长绑定同一学生。
- 家长端只能查看已绑定学生的允许信息；越权访问未绑定学生必须被拒绝。

### Teacher Validation

- 班主任必须是教师及以上角色，且用户处于有效状态。
- 科任老师必须是有效教师、属于当前学校，并具备对应学段/科目权限。
- 前端老师选项和后端保存校验必须一致，后端不能只依赖前端过滤。

## Acceptance Criteria

- 班级列表可按入学年份、学段、动态当前年级、状态组合筛选。
- 班级详情返回学生数、学生总数、班主任、科任老师、动态当前年级、状态、历史记录。
- 小学六年级在新学年触发后变为已毕业，不再出现在新建学生、批量导入和新 AI 任务的可选班级中。
- 学生列表可按入学年份、动态当前年级、班级、状态筛选，并可按姓名、系统账号、手机号搜索。
- 学生详情能按时间倒序展示修改历史。
- 新学生导入接口支持上传解析、确认导入、异常行查询、修正后重新校验、导入已修正数据。
- 新学生导入不修改旧批量导入用户接口。
- 新学生导入确认成功后，每个学生都有 `users` 账号、`user_profile` 学生档案、`STUDENT` 角色和学生实体绑定关系。
- 导入时提供多个家长手机号的学生，会创建或复用多个家长账号，赋予“学生家长”角色，并在 `parent_student` 中建立多条有效绑定。
- 导入时未提供家长手机号的学生仍可导入成功，并可通过补录接口后续绑定家长。
- 学生账号生成结果全局唯一且不超过 18 位；冲突场景有可测试的重试策略。
- 学生默认密码由配置控制，导入后能识别默认密码状态，但本期不开放默认密码登录改密流程。
- 班主任和科任老师保存时均校验身份、状态、学校和权限边界。

## Open Questions

- 是否允许学校级配置覆盖默认 8 月 15 日新学年触发日。
- 家长手机号是否允许多个学生共用。
- 重复学生合并规则由后端直接执行，还是先返回合并建议由前端确认。
- 异常数据是否需要支持失败明细文件下载。
- “学生家长”角色的精确菜单和权限清单需要结合前端家长端页面再细化；当前 PRD 只要求能查看已绑定学生的受限信息。
